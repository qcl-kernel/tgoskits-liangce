# 基于 AxVisor 的混合关键系统智能控制原型设计说明

## 1. 建设目标

本原型在同一 AArch64 虚拟化平台中承载智能计算与实时控制任务，验证以下能力：

1. 由 AxVisor 隔离运行 Linux 与 Zephyr 两类 Guest；
2. 在不暴露 Guest 内存给外部网络设备的前提下，提供 Guest 间内部 IP 通信；
3. 由 Linux 执行轻量神经网络推理并下发控制量，由 Zephyr 执行周期控制、对象更新和状态反馈；
4. 在通信超时、进程异常、非法控制量或队列过载时进入有界安全状态；
5. 以统一事件格式、运行清单和文件哈希支持结果复核。

## 2. 总体架构

```text
                     QEMU AArch64 virt
┌─────────────────────────────────────────────────────────────┐
│                         AxVisor                             │
│  ┌──────────────────────┐      ┌────────────────────────┐  │
│  │ Linux Guest          │      │ Zephyr Guest          │  │
│  │ - 状态接收           │      │ - 100 ms 周期任务     │  │
│  │ - MLP 推理/PI 对照   │      │ - 一阶温度对象        │  │
│  │ - CONTROL 下发       │      │ - 动作应用与 STATUS   │  │
│  │ - 闭环指标           │      │ - 500 ms 安全看门狗   │  │
│  └──────────┬───────────┘      └───────────┬────────────┘  │
│             │ VM-local VirtIO-net          │               │
│             └──────────┬───────────────────┘               │
│                        │ vnet0                             │
│       scoped Guest-memory copy + bounded L2 switch         │
└─────────────────────────────────────────────────────────────┘
```

原型采用 QEMU `virt`、Cortex-A72、GICv3、4 个物理 CPU 和 8 GiB 外层内存。Linux 固定使用 pCPU 0、1，Zephyr 使用 pCPU 2，pCPU 3 留给宿主与控制台处理。Linux 使用至少 2 个 vCPU，Zephyr 使用 1 个 vCPU。

## 3. 虚拟化与资源隔离

AxVisor 负责虚拟机生命周期、CPU 和内存分配、设备声明、Stage-2 地址转换、Guest FDT 生成以及中断归属。

- Linux 内存规划为 256 MiB，Guest 物理地址起点 `0x8000_0000`；
- Zephyr 内存规划为 128 MiB，Guest 物理地址起点 `0x4000_0000`；
- 每个 Guest 仅能看到自己的虚拟设备、MMIO 和中断资源；
- 网络设备使用短生命周期、按 VM 授权的内存访问能力进行 CPU copy，不保存裸宿主指针或跨 VM 内存视图；
- 设备销毁时先停止端口并清空入口队列，旧代次的端口和帧不能在新会话中恢复生效。

## 4. 内部网络设计

Guest 间网络采用 AxVisor 内的软件中介 VirtIO-net：每个 Guest 拥有一块独立 VirtIO-MMIO frontend，两端通过仅含两个端口的内部二层交换面 `vnet0` 连接。

关键边界如下：

- VirtIO-MMIO v2、split virtqueue，RX queue 0、TX queue 1，队列长度 256；
- 帧长度范围 14 至 1514 字节，链路 MTU 1500；
- 每端入口队列容量 64 帧，队列满时丢弃新帧；
- 仅协商版本、MAC 和链路状态所需特性；
- 不使用外层 QEMU 网卡、TAP、bridge、NAT 或设备直通作为 Guest 间主链路；
- 发送路径先完整校验 descriptor chain 和 VirtIO-net 头，再复制到宿主拥有的帧；接收路径只向完整可写链复制；
- 每个 frontend 的 virtqueue、寄存器、中断、内存授权和生命周期状态完全独立。

固定网络参数：

| 项目 | Linux Guest | Zephyr Guest |
|---|---|---|
| MAC | `02:00:00:00:00:01` | `02:00:00:00:00:02` |
| IPv4 | `10.77.0.1/24` | `10.77.0.2/24` |
| 路由 | 仅 `10.77.0.0/24` 直连 | 仅 `10.77.0.0/24` 直连 |
| UDP 主端口 | `46000` | `46000` |
| TCP 回退端口 | 主动连接 `10.77.0.2:46001` | 监听 `10.77.0.2:46001` |

## 5. 通信协议

应用层采用 ICCP（仓库实现名 ICPC v1）。ICPC v1 使用 36 字节网络字节序头、CRC32C 校验、会话编号、序列号、确认序列号和有限接收窗口，消息类型包括 CONTROL、STATUS、ERROR、ACK 和 HEARTBEAT。

UDP 是主传输：每个 UDP 数据报恰好包含一个 ICPC 包。CONTROL 和 ERROR 要求确认；STATUS 与 HEARTBEAT 为尽力发送。通用重试间隔为 100、200、400 ms；CONTROL 的有效期固定为 500 ms，因此仅允许在 0、100、300 ms 发送，到 500 ms 未确认即取消旧会话控制并进入 TCP 回退，不得在 700 ms 重发过期控制。

TCP 回退采用 2 字节大端帧长加完整 ICPC 包，解析器处理部分读取和一次读取多个帧。UDP 与 TCP 切换必须创建新会话，旧会话控制包不能重新取得执行权。

## 6. 控制对象与智能控制器

控制对象是一阶温度模型，Zephyr 每 100 ms 更新一次。CONTROL、STATUS、ERROR 业务载荷分别固定为 24、32、12 字节；温度单位为毫摄氏度，动作是 `[0,1]` 范围的 Q16.16 加热占空比。

Linux 提供两种走完全相同网络和协议路径的控制器：

- 固定 PI 控制器，用作可解释对照；
- `3→8→1` 轻量多层感知机，隐藏层使用 ReLU，输出层使用 sigmoid。

模型输入固定为测量温度、目标温度和上一周期占空比，输出为新的加热占空比。模型版本、权重、归一化参数、生成配置、黄金向量和文件哈希共同构成可复现输入。

固定对照场景时长 180 s，初始温度与环境温度均为 25,000 mC，目标温度为 55,000 mC，并在 60 至 90 s 注入每周期 -150 mC 的扰动。评估指标包括 RMSE、IAE、稳定时间、超调量以及 Linux 同钟闭环往返时间。

## 7. 实时与安全设计

- Zephyr 的对象更新和动作应用位于高优先级周期任务，socket、协议解析和日志位于较低优先级线程；
- 网络线程只把最新的有效命令投递到有界单元素 mailbox，周期任务不等待网络、日志或模型；
- 500 ms 内未收到新的有效 CONTROL，Zephyr 进入安全状态并撤销旧动作；
- 重复、乱序、旧会话、非法范围或模型版本不匹配的命令不能刷新安全看门狗；
- 队列过载、协议错误、控制超时、模型异常和运行时溢出均以状态位或 ERROR 消息观测；
- 协议不提供认证、加密或抗重放能力，部署安全依赖隔离网络和严格端点约束，不将其描述为密码学安全。

## 8. 测量与证据设计

所有关键事件使用单调纳秒时钟记录。闭环延迟在 Linux 同一时钟域内，由输入 STATUS 接收事件到带匹配请求编号的反馈 STATUS 接收事件计算；Zephyr 应用延迟在 Zephyr 同一时钟域内计算，不使用跨 Guest 单向时间差作为结论。

每次运行应形成独立会话目录，并记录：

- 上游基线、候选源码版本和工作树状态；
- QEMU、AxVisor、Guest 镜像、配置、模型和依赖哈希；
- 双 Guest 启动、最终 FDT、资源声明、网络配置、抓包和事件日志；
- 原始样本、统计结果、运行状态和文件校验和；
- 测试命令、开始结束时间、退出码、失败原因及未证明边界。

失败运行同样保留，后续运行不得覆盖。静态合同、主机测试、目标构建、单 Guest、双 Guest、Guest IP、控制闭环和长稳是逐级证据，低等级结果不能替代更高等级运行验证。

## 9. 交付范围

基础交付目标为 QEMU AArch64 上的 Linux 与 Zephyr 双 Guest 原型。最终成果由源码与配置、构建和测试脚本、模型与模型卡、设计与复现文档、当前候选版本测试记录、证据索引、演示材料和完整性校验组成。大型镜像、抓包和原始日志不直接进入代码仓库时，应提供可访问归档地址、大小和 SHA-256。
