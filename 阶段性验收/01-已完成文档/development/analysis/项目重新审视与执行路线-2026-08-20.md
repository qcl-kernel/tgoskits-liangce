# 项目重新审视与执行路线（2026-08-20）

本文把两份原始申报材料、当前开发工作树、immutable evidence、最新官方 `rcore-os/tgoskits dev` 和官方 PR 检查放到同一基线上。它回答“为什么难、哪里最不确定、接下来按什么顺序开发”。任务状态仍以 `development/current/` 四账本和 `contest/contest-spec/` 为权威；本文不把分析升级为 runtime 证据。

## 1. 结论

原始目标不变，但原始实现排期需要纠偏：

1. 主交付保持 QEMU AArch64 上的 AxVisor + Linux（或可替换的 StarryOS）+ Zephyr 双 Guest；RISC-V 和实体板只作为时间允许时的增强，不阻塞主交付。
2. TCP/UDP/IP 与 ICPC 是主数据链；console、共享内存、HyperCall、vsock 和 host socket 只能用于诊断，不能替代 Guest IP。
3. P2 的资源隔离、双 Guest、1,800 秒共存与窄 virtio-blk 字节效果已经提供足够前置。原始任务并不要求证明通用 IOMMU/SMMU 或硬件 DMA isolation，因此停止扩大 P2 DMA 研究。
4. P4 已取得真实 mediated `vnet0` 的 ICMP/UDP/TCP/ICPC **窄冒烟**，但当前 runner/profile 只验证 marker 与 cleanup，不能关闭完整 TEST-011..015。
5. P5 的 host 模型、plant、mailbox、watchdog 和协议部件可立即接入目标应用；P5 happy-path 开发可以和 P4 可靠性并行，但 P5 资格验收必须等待 P4 完整可靠性门禁。
6. P3 的事件 schema、统计和只读采集可提前；生产 A/B 必须在官方上游适配和 P4/P5 生产路径冻结后重采基线，避免比较不同设备/调度语义。
7. 项目交付仍禁止 PR；使用本地提交、私有比赛仓库和离线 patch/manifest。官方 README 的通用 PR 流程不覆盖本项目的明确禁止规则。

## 3. 最困难与最不确定

### 3.1 最困难的即时任务：在移动的官方设备模型上前移 P4

本地 P4 已经能运行，但官方 #2092 改了同一生产文件和设备访问接口，#2105 又改了 CI 接入方式。困难不在“写一个网卡”，而在同时保留：issuing-vCPU 身份、短生命周期 Guest memory access、Auto 资源、resolved FDT、level IRQ、bounded switch、reset/destroy 失效和现有 Linux/Zephyr 行为。任何一个边界丢失都可能出现“能 ping 但隔离或生命周期错误”。

解决方案是新增 `P4-UPSYNC-02`，只做一次固定官方观察点上的手工前移，不在测量期间持续追 `dev`。旧 evidence 保留历史级别；新 HEAD 必须重新建立 build 和 runtime evidence。

### 3.2 最大的不确定：适配后运行语义是否仍正确

静态 diff 可以给出端口方式，但不能回答以下问题：

- `DeviceContext` 是否始终携带正确 issuing vCPU，跨 vCPU/跨 VM/旧 generation 是否被拒绝；
- level IRQ 的 assert/deassert 是否在新 device runtime 中保持；
- resolved graph 写入 final DTB 的 MMIO/IRQ 是否与运行时实例一致；
- Linux/Zephyr 在相同 workload 下是否还保持 100/100，而不是只通过偶然 marker。

解决它只能靠分层门禁：host negative tests → AArch64 build → 官方 peer demo → fresh Linux+Zephyr smoke → scenario-specific qualification。文档不得用官方 PR CI 代替本项目 runtime。

### 3.3 最容易误判的地方：P4 evidence 发布语义

当前 runner 找到 completion marker 且 cleanup 成功就发布 `guest_network_completed`，但并未强制场景计数、PCAP/capture、metrics、双向/fault 语义；host-only profile 也被 runtime runner复用。这会让开发者把 85/100 的 ICPC 冒烟误写成 TEST-015 完成。

解决方案是 `P4-EVID-01`：

- 保留 v1 host-only profile/validator，只用于 L2 fixture；
- 新建 guest-runtime profile/schema，绑定 QEMU identity、nonce、两份 final DTB、两 Guest READY、镜像/config/hash；
- 状态拆为 `guest_network_smoke_completed` 与 `guest_network_qualified`；
- 场景 validator 解析结构化计数而非子串；TEST-015 资格模式要求 1,000 CONTROL、10 Hz/100 s、fault/restart、每条恰应用一次或显式取消，85/100 必须失败；
- runner 必须发布 frame JSONL、PCAP、counters、metrics、fault manifest、session/result/status-last 和 cleanup report；空 `network/`/`metrics/` 不得成功。

### 3.4 P3 与 P5 的不确定

- P3：双 Guest 下 Zephyr 虚拟时钟曾表现出速率波动，且上游 scheduler/device/timer 仍在变化。官方 `ax-tracepoint` 是可选的 no_std 原子 gate 采集基础，但当前目标是 AxVisor+Zephyr，不是 Starry tracefs；必须先做 `P3-TRACE-FEAS-01`，证明 linker、时钟域和开销适用，否则继续使用已有专用 Zephyr probe/IF-010 schema，不为复用而扩范围。
- P5：模型/plant 的 host 部件已经足够，真正未知是 Guest 内模型数值一致性、Zephyr 周期线程不被网络阻塞，以及 watchdog/restart 后唯一 actuator owner。通过 canonical model + golden vectors + target build + happy-path session + fault qualification 逐层消除。

```text
P2（已冻结）
  -> P4-UPSYNC-02（官方 21ef 上的设备 API + CI v3 前移）
  -> P4-EVID-01（runtime schema/runner/validator 修正）
  -> P4-SMOKE-02（新 HEAD 重跑 NIC/ARP/ICMP/UDP/TCP/ICPC）

  -> P5-AI-C（happy-path 闭环）
  -> P5-AI-Q（fault/safe-state/固定策略对照；依赖 P4-REL-01）
  -> P3-TRACE-FEAS-01 + P3-RT-01（当前生产路径重采 baseline 与 A/B）
```

P5 提前并行只允许实现与 happy-path 调通；它不能用 P4 冒烟替代可靠性资格，也不能提前发布 AI-loop 完成结论。

- host oracle：resource conflict/Auto、wrong-vCPU、cross-VM、stale generation、queue overflow、IRQ assert/deassert、CI plan routing 全部有负例。
- 需用户明确确认后运行：WSL rustfmt/test/clippy/AArch64 build 与 QEMU。
- 完成：固定新 HEAD；host/target gate 全绿；无第二套 backend；旧 evidence 不升级。

### 5.2 P4-EVID-01 与 P4-SMOKE-02

- 先以 TDD 修改 `scripts/contest/network/` 与 `configs/contest/network/`：错误 marker、计数不达标、空 capture/metrics、错 DTB/nonce、cleanup 残留必须红。
- fresh run 依次执行 NIC枚举/ARP/双向 ICMP → UDP → TCP fallback → ICPC happy path。每个场景使用新 evidence 目录。
- 冒烟成功只关闭 `P4-SMOKE-02`；只有 TEST 表全部 oracle 和工件满足才关闭资格测试。

### 5.3 P4-REL-01

- TEST-012：每方向 10,000 个 256-byte UDP echo + 固定 fault seed；逐包对账、PCAP、吞吐/RTT/重传指标。
- TEST-013：10,000 framed messages、partial/merged read、disconnect/restart/half-frame EOF、新 session 与唯一 owner。
- TEST-015：1,000 CONTROL、ACK/STATUS、drop/duplicate/reorder/corrupt/version/length/restart/timeout；恰应用一次或显式取消，silent loss=0。

### 5.4 P5-AI-A/B/C/Q

- A：冻结 `3→8→1` float32 model、metadata、dataset/golden vectors/checksums；Linux target C 推理逐向量一致。
- B：Linux 用真实模型输出 CONTROL；Zephyr 把 CONTROL 写入 one-element mailbox，在 100 ms 周期边界应用，STATUS 来自真实 plant/action，500 ms watchdog 独立安全回退；删除占位 `0x44` STATUS。
- C：同一 session 完成 input→inference→UDP/IP→action→STATUS feedback，绑定 model/hash/request/sample。
- Q：三个 seed、固定 PI 对照、至少两个指标、网络故障与 controller restart，证明 safe-state 和恢复；依赖 P4-REL-01。

### 5.5 P3-RT-01

- 先做 `P3-TRACE-FEAS-01`：选择统一时钟，量化 trace 开销，确认 passthrough/virtual timer 的实际路径；缺席事件必须 N/A，禁止伪造。
- 在最终 P4/P5 生产路径上重采 native/idle/cpu/net/ai/combined，每场景 3 run，每 run ≥100,000 样本或 ≥1,800 秒。
- 最多选择两项默认关闭的优化，使用同配置/同镜像/同 seed A/B；发布 mean/max/P99/P99.9、原始事件、统计脚本和回滚开关。

## 6. 新开发者的唯一入口

1. 读 `AGENTS.md`、`development/README.md`、`development/current/开发交接.md`。
2. 运行交接文件顶部的只读 preflight，确认目录、HEAD、upstream SHA 和 dirty 文件与记录一致。
3. 只领取 `development/current/计划.md` 顶部标为“可执行”的一个工作包；阶段细节读对应 P2–P5 手册。
4. 编码前写清 allowed paths、red test、green oracle、证据等级、需用户确认的 WSL/QEMU/push 操作。
5. 先确定性 host 测试，再 target build，再 fresh runtime；任何失败保留新目录并登记 primary/cleanup。
6. 同步更新规范、四账本和镜像；禁止 PR、禁止覆盖 evidence、禁止用低等级证据升级结论。
